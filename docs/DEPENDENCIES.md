# External dependencies and the assumptions behind them

This app is a client for other people's software. Almost everything that has broken it broke
because a harness behaved differently from what the code assumed — not because of a logic error.
This file records what we depend on, what we assume from it, and what to check when it changes.

Keep it current. An assumption that is not written down is one nobody will re-check.

## Harness surfaces

### OpenCode — HTTP API

Spoken directly, no adapter. The app calls `/global/health`, `/global/event`, `/session*`,
`/config/providers`, `/command`, `/agent`, `/project/current`, `/vcs`, `/file*` and `/question*`.

**Assumed:** the server emits an SSE heartbeat roughly every 10s. The client aborts and reconnects
after 30s of silence, so a server that stops beating looks dead.

**Watch:** new or renamed endpoints, and the event envelope shape (`{directory, payload}`).

### Oh My Pi (OMP) — ACP over stdio, via `omp acp`

First-party command, no third party in the path. The bridge uses `session/new`, `session/load`,
`session/list`, `session/prompt`, `session/cancel` and `session/set_config_option`.

**Assumed, all observed on OMP 17.1.3 rather than read from a spec:**

| Assumption | What breaks if it changes |
|---|---|
| `session/list` returns no `title` | titles are derived from the first prompt; a real title would be ignored |
| A submitted prompt is never echoed back as `user_message_chunk` | the deduplication acknowledgement would swallow the user's message |
| Chunks carry a `messageId` | without one, chunk aggregation falls back to per-turn tracking |
| No `agent_plan` is emitted | the todo panel stays empty by design |
| The agent approves its own tool calls and never sends `session/request_permission` | the permission path would start being exercised |

**Watch:** any of the above, and new `sessionUpdate` kinds we silently ignore (`tool_call`,
`tool_call_update` and `agent_thought_chunk` are dropped today).

### OMP Collab — encrypted WebSocket wire protocol

Collab attaches one arbitrary desktop-started OMP session after its bearer link is pasted into the
app. It is not a global OMP session-discovery API. The wire contract comes from
`@oh-my-pi/pi-wire`, pinned exactly to **`17.1.8`** in `web/package.json`; do not float this
dependency.

**Assumed:**

| Assumption | What breaks if it changes |
|---|---|
| A link identifies `/r/<room-id>` and carries a base64url room secret, either as `<room-id>#<secret>`, in a viewer URL fragment, or after the room ID in a relay URL | links generated by OMP stop attaching |
| The secret is the 32-byte room key followed optionally by a write token | key import fails, or a read/write link is mistaken for read-only |
| The room key is bearer authority to decrypt/read the room; the optional write token additionally authorizes `prompt`, `abort`, and UI-response frames | leaking a link leaks its granted access; removing UI controls alone would not revoke a leaked token |
| A missing write token means read-only, with no prompt, abort, or reply controls | a viewer could be offered actions the host will reject, or could gain unintended write authority |
| The guest opens `/r/<room-id>?role=guest`, sends an encrypted `hello` with the protocol version, name, and optional write token, then receives `welcome`, all declared snapshot chunks in order, and only then live entries/events/state | accepting live frames too early produces incomplete or out-of-order history; a changed handshake leaves the attachment waiting or ended |
| Binary frames are WebSocket envelopes containing an AES-256-GCM ciphertext with a fresh 12-byte IV; encryption/decryption occurs on the endpoints, so the relay never receives the room key or plaintext | a cipher, IV, envelope, or framing change makes frames undecryptable or unauthenticated |
| Custom non-local relays use `wss://`; plaintext `ws://` is accepted only for loopback development | bearer metadata and traffic could otherwise cross an untrusted network without transport security |

Collab links must never be logged or sent to the bridge. Runtime snapshots remain in memory; only
the attachment metadata and bearer link persist, through iOS Keychain as described below.

**Re-test:** every `@oh-my-pi/pi-wire` or OMP Collab version change, and every change to link
parsing, protocol/frame ordering, WebSocket behavior, Web Crypto/AES-GCM, or relay configuration.
Exercise full and read-only links, prompt/abort/reply authorization, snapshot ordering, reconnect,
and rejection of tampered ciphertext against a real OMP `/collab` session before changing the pin.

### PI — ACP over stdio, via a third-party adapter

This is the only dependency that is neither ours nor first-party, and the one to watch hardest.

- **Adapter:** [`@automatalabs/pi-acp`](https://www.npmjs.com/package/@automatalabs/pi-acp),
  Apache-2.0, in [`VikashLoomba/agentprism-workflows`](https://github.com/VikashLoomba/agentprism-workflows)
  under `packages/pi-acp`. Single maintainer (`automatalabsteam`).
- **Pinned to `0.2.5`** in `bridge/src/harness-profiles.js`.
- **It is young and moves fast:** first published 2026-07-16, eleven versions in the following ten
  days. Treat a bump as a change worth testing, not a routine refresh.

**Why an adapter at all.** PI's maintainer
[declined native ACP support](https://github.com/earendil-works/pi/issues/175), suggesting an
adapter over PI's own RPC mode instead. Several exist. The other widely referenced one,
`@victor-software-house/pi-acp`, declares `engines.bun` and shells out to `bun`; this project runs
on Node everywhere, which is why it is not used.

**Why the version is pinned.** An unpinned `npx -y` default failed live with `notarget`: version
`0.2.6` was in the npm index and tagged `latest` while its tarball was not yet fetchable. A
floating default breaks whenever an upstream publish goes wrong.

**Assumed:**

| Assumption | What breaks if it changes |
|---|---|
| Launched over stdio as an `npx`-installable `bin` | the `--acp-command` / `--acp-arg` defaults in the profile |
| Offers a non-`env_var` auth method (`pi-stored-credentials`) | the bridge would fall back to an API key from an unset environment variable and fail at inference |
| Asks `session/request_permission` before each tool call, offering an `allow_once` option | tool calls stop happening, silently — the failure mode is "reports success, changes nothing" |
| Streams chunks with **no** `messageId` | replies would split into one message per token, or aggregate wrongly |
| Emits no `agent_plan` | the todo panel stays empty |

**The adapter embeds its own PI.** It depends on `@earendil-works/pi-coding-agent` pinned to a
specific version (`0.82.1` in adapter 0.2.5), so the PI that actually runs is the one bundled with
the adapter, not the `pi` on your PATH. Your local install still matters for configuration and
credentials, which it reads from disk. Two consequences:

- updating `pi` locally does not change what the bridge runs;
- the adapter can lag PI releases, so a PI feature can exist locally and be unavailable here.

**Exit route.** If the adapter becomes unmaintained or unreliable, PI's own RPC mode
(`packages/coding-agent/docs/rpc.md` in the PI repo) is the first-party alternative. It means
writing a transport in the bridge rather than reusing the ACP client, but it removes the third
party entirely.

## App, networking, and iOS packaging

- **Capacitor 8** (`@capacitor/core`, `/ios`, `/cli`, `/app`) wraps the React/Vite app for iOS.
  It requires iOS 15+ and Xcode 26+; older deployment targets or toolchains are unsupported.
  `web/ios/` is generated and ignored: rebuild the web app, add iOS once with
  `npm run cap:add:ios`, and regenerate/sync with `npm run cap:sync:ios` rather than treating the
  Xcode project as hand-maintained source. A stale or version-mismatched generated project can omit
  current web assets, plugins, or native configuration.
- **WebKit fetch/SSE is a known transport risk.** Ordinary native HTTP uses Capacitor HTTP, but
  authenticated direct-session event streaming still relies on JavaScript `fetch` in the iOS
  WebView. Its exact origin is `capacitor://localhost`, so every bridge used by the IPA must be
  launched with `--cors capacitor://localhost`. Re-smoke direct session create/select, prompt
  streaming, stop, and reconnect on a real iPhone after every relevant Capacitor, iOS, WebKit, or
  SSE transport change; a regression can buffer or drop events even when ordinary Capacitor HTTP
  requests still succeed.
- **Swift Keychain integration is required.** Collab bearer links have no `localStorage`,
  IndexedDB, or plaintext-file fallback. If the native Keychain plugin is absent or fails,
  attachment persistence must fail closed rather than copy the secret into web storage.
- **Tailscale is an external network dependency, not an app dependency.** Install and authenticate
  it separately on the iPhone and bridge host. The app only uses the host's MagicDNS name or
  tailnet IP; it neither authenticates Tailscale nor stores Tailscale credentials. Tailnet routing,
  ACLs, and availability remain the user's responsibility, and bridge Basic Auth is still required.
  If either device is outside the intended tailnet path, remote direct mode cannot connect; the app
  provides no fallback tunnel.
- **Sideloadly** installs the Xcode-archived/exported IPA; there is no App Store or TestFlight
  workflow. Installation validity follows the Apple signing profile. Free Apple IDs commonly need
  re-signing and reinstalling every seven days; paid profiles can last longer but are still bounded
  by their actual expiry. An expired profile stops the installed app from launching.
- **React 18, Vite, `react-markdown`, `remark-gfm`** are ordinary frontend dependencies.
- The **bridge has no dependencies at all** and runs on the Node standard library. Keep it that
  way: it is the piece that has to start reliably on someone else's machine. The CLI enforces
  paired `--username` and `--password` values and requires both for any non-loopback LAN or
  Tailscale listener. With no `--root`, however, the allowed root defaults to the bridge process's
  current working directory; this guide additionally requires an explicit `--root` for every
  non-loopback deployment. The bridge must never be exposed directly to the public Internet.

## When a harness changes

Unit tests will not catch this. Every quirk in the tables above was found by running a real agent,
and the fakes in `bridge/test/` only lock in what was already learned.

1. Run the harness for real: create a session, send a prompt, watch the reply stream, run a prompt
   that uses a **tool**, and stop a run.
2. Check whether a tool call actually did something. "Reported success and changed nothing" is the
   signature failure here.
3. Reopen a session and confirm the history is intact and in order.
4. Compare what you see against this file's tables, and update them in the same commit as the fix.
5. Update the capability matrix in `bridge/src/harness-profiles.js` if the harness gained or lost
   something.

For a version bump of the PI adapter specifically, the pin in `harness-profiles.js` is deliberate:
change it consciously, run the checks above, then commit the new pin.
